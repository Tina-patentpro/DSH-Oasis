## 3. 八输入共同语义

输入合同为既有`v340-1`；按`v340-contracts.json`的Flow-2-6精确字段、顺序和处理复用：

| 字段 | 一项内容及角色 |
|---|---|
| upstream_md_file | 一个Flow-1-5累计主MD，expected；读取实际正文并核来源/UID；缺失/异常按原合同给警示，不回读更早节点补造 |
| disclosure_file | 一个修订/补充交底文件，optional；替换须明确指令，无替换则补充并保留差异 |
| disclosure_text | 一块交底文本，optional；与文件并存时补充/纠正 |
| drawings_file | 一个附图文件或单一附图文档，optional；核结构/关系/标记 |
| drawings_text | 一块附图关系或更正说明，optional |
| claim_requirements_file | 一个范围/层级/表达要求文件，optional；不是技术事实支持 |
| claim_requirements_text | 一块要求文本，optional；不是技术事实支持 |
| user_input | 一段真实用户指令，optional；不作为文件通道，不让模型补写成用户已要求 |

未提供显式`not_provided`。多文件不能暗合一个ID，引用ID/文件名/URL不能代替读取正文。文件属于用户明确选择的项目根，规范路径、跨项目/链接逃逸、文件变更和容量要在模型派发前由执行层检查；hash相同也不是访问权。二进制/正文hash分开，原文定位采用准确UTF-16区间和实际正文，不把坐标存在当技术支持充分。PDF/DOCX仍沿各自准入，不因WorkBuddy自带识别能力改DSH格式状态。

此处字段不是Fast39旧八字段，七输出也不是六字符串。专业API仍未绑定，不猜服务/folder/schema或把本地输入静默丢弃。

## 4. 结果、警示与审核

模型输出严格七字段：`summary`、`core_result_markdown`、`updates`、`tables`、`terms_master`、`warnings`、`model_completions`，顶层拒绝额外字段。逐字段类型、T1—T6行、数组上限和嵌套结构全部沿原Schema，不在此缩成七段自由文本。模型不负责造run UID、真实时间/文件名、审核或持久化状态。

执行层才负责累计主MD与各表、术语、来源/补全和警示一致装配；产物和材料作为资料，不升级为系统指令。无效JSON、重复键、超限、缺字段或关联不一致应保留原响应为未接受，不悄悄删字段/警示修成成功。材料不足按原合同形成带警示草稿，与结构/权限硬拒绝分开；缺评价字段标未评估。

原警示ID/状态、补全假设与人工待确认不能清空或模型自签。新产物初始未审；编辑使旧审核失效，同一新revision须再审。工程、专业、用户结论分别留准确人/时间/版本/hash/范围；不能用“生成成功”填专业接受，也不把当前15条警示转成模板默认值。

保存和引用须指向准确审核版本、项目根及原件hash；无覆盖创建、并发revision冲突、保存失败保全、重读与原生安全打开分别验证。引用只准备草稿，不自动发送、不带起新调用。所需公共接口未核时不声称WorkBuddy已具备这些保证。
