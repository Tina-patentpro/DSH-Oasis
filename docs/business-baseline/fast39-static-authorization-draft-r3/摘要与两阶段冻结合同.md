# Fast39例外摘要与两阶段冻结合同

合同ID：`FAST39-EXCEPTION-HASH-FREEZE-1`；授权文档R3的组成部分。**待审、未批准、不可执行。** 本合同处理R2-TR01／02，不改变C4协议、A的四字段或原工具代码。机器定义见[hash-and-freeze-contract.json](hash-and-freeze-contract.json)，最终例外意图形状见[exception-intent.schema.json](exception-intent.schema.json)。

## 1. 三种摘要各自计算什么

| 名称 | 准确输入与算法 | 记录位置 |
|---|---|---|
| `request_original_sha256` | 最终请求文件完整原字节B的SHA256，小写64位十六进制。包括实际缩进、空白和末尾换行；不解析后重写、不归一化 | F1外部清单、提交门和真实例外回执；不写入请求自身 |
| `exception_intent_sha256` | 严格解析B得到最终对象I，按下述规范序列化**完整I，排除字段集合为空**，再对无末尾换行的UTF-8字节求SHA256 | B这一次例外的`registry_transaction.request_sha256`，及F1／提交门／例外回执 |
| `ordinary_native_intent_sha256` | 普通请求去掉`expected_revision`、`expected_sha256`，用原工具`canonical`后求UTF-8 SHA256 | 原工具普通started／progress／completed请求与回执证据；算法保持原样 |

完整例外意图的规范序列化精确等价于：

```python
json.dumps(I, ensure_ascii=False, sort_keys=True,
           separators=(',', ':'), allow_nan=False).encode('utf-8', errors='strict')
```

对象键排序，数组顺序不变，不做Unicode规范化、路径重写或字符串换行转换；没有额外终止换行。输入须是严格UTF-8、无BOM的JSON对象；所有层重复键、浮点数、NaN／Infinity、孤立代理码、未知字段、null／未填占位均拒绝。整数字段不接受布尔值。解析后仍须通过冻结Schema及本合同跨字段检查。

例外摘要包含`baseline`及全部审批／机制／setup／操作／保护／治理输入。只改变基线也必须改变例外摘要。**这有意不同于普通事务意图摘要，属于B须明确批准的一次性摘要产生规则例外。** 原锁、元数据派生／校验能力继续复用；不再笼统声称所有摘要语义与原工具相同。不改登记六字段形状、全局schema值或`registry_changes_only`语义，也不修改原工具。

同一意图的两种排版可能具有相同意图摘要和不同原件hash；两者都须与F1和提交门一致。意图等价不授权重排已冻结原件。原工具校验不会重算外部意图、认证审批或写入者；Schema通过只是一层结构证据。

## 2. 最终请求的准确字段及外部证据

顶层字段只有：`kind`、`intent_version`、`transaction_id`、`owner_scope_id`、`work_item_id`、`approval_bindings`、`mechanism`、`baseline`、`setup_receipt`、`operations`、`protected`、`governance`。每层准确字段、类型及常量由Schema限定，不接受额外键。

- `kind=fast39_registry_structure_exception`、`intent_version=1`，明确不是普通apply请求；禁止送入普通apply，普通算法不用于其事务摘要。
- `approval_bindings`指R3冻结包和**F0之后产生的前置授权**，标明setup授权ID及`commit_mode`。它不含引用最终请求的后置提交批准。
- `mechanism`固定真实脚本、意图模板和原工具的路径／原字节hash；`baseline`固定setup已确认成功后的真实源README路径、revision和完整hash。
- `setup_receipt`绑定普通started请求原件hash、原工具意图摘要、真实返回原件、事件ID、真实post-setup revision／hash和自身工作项原行hash。仅有`idempotent=true`或工具当前整册hash不能证明这一具体setup成功，必须对照保存的前后字节、对应事务和归属。
- `operations`精确等于B两处已批准变化；`protected`绑定Flow2-6、10157、准确表头／原行hash及完整保护清单；`governance`绑定真实正常周报、哨兵及新鲜exit0证据。这些前置原件不能包含后来的最终请求／提交门／提交结果hash。

跨字段检查必须证明：baseline与setup真实后版本相同；引用原件真实存在、在批准范围、非链接且hash匹配；owner／空grants不可变；两处变化、全部旧事件／归属／14业务行保护成立；R3与前置授权真实覆盖本模式和机制；两种摘要独立重算匹配；transaction_id未用；新事件ID准确为`REG-TXN-`加该ID；事务base准确为锁内原字节hash，新revision只加1。仅Schema通过不能代替这些检查。

## 3. 冻结顺序和授权边界

| 阶段 | 冻结对象及事实 | 可允许的源动作 |
|---|---|---|
| F0 普通started之前 | R3身份；实际脚本／模板／原工具及有界实例化规则；**完整普通setup请求**的原件hash／原工具意图摘要和pre-setup基线；拟采用的commit模式。F0清单不含未来授权文件hash | 只有在另有明确B_SETUP授权和正常CI／新鲜治理0后，普通原工具可建立本次修复工作项及空grants |
| setup确认成功后形成F1 | 保存真实setup前后字节／请求／返回；只接受这一笔自身setup的合法差异。绑定真实post-setup基线和前置授权，再冻结最终例外请求、两种摘要、完整私有候选字节／差异／hash和保护证据 | F1形成和复核本身不写源，不要求未知最终请求在普通started之前已存在 |
| 外部提交门及B_COMMIT | 在F1之后独立记录准确F1清单、请求原件hash／意图摘要、候选／差异／基线及真实授权。重新独立核对，不把门回写到请求自身 | 获准的固定机制在原锁下重读、复算、重现冻结候选并校验，才允许一次例外原子提交 |
| 例外提交之后 | 如实记录实际锁／替换／读回、真实前后hash和错误／未知；新鲜完整治理和严格行检查；再普通记录自身进展／结束 | 实际结果证实后才按既有B生命周期记录，不暗授A静态候选生产 |

当前所有实际阶段产物和授权均未形成。F0／F1是不同对象，不在执行中改名混用，也不从本轮观察489推填未来expected。F0在正常周报和CI动作完成后，以当时真实源基线形成；原业务行、两处待恢复字节及其他固定输入仍须匹配批准范围。

### 3.1 一份准确授权可覆盖两阶段

F0冻结后，前置授权须明确B_SETUP，并明确下列一种commit模式：

- `preapproved_conditional`：同一准确授权明确接受R3的完整意图摘要差异、固定F0／脚本／模板和有界实例化规则，并有条件覆盖B_COMMIT。F1只能填入真实自身setup及批准类别的证据，不改操作／机制／范围。受权执行者仍须在F1后形成真实技术提交门，不能由检查通过自行创造权限。
- `separate_approval_required`：前置只准setup；F1冻结后，须取得准确F1提交批准才能写结构。该后置批准在请求之外引用F1，不加入请求自引用。

不能从泛称“继续”、setup-only批准或技术复核通过推导commit模式。已有明确同范围条件授权可沿用，不逐阶段重复索取；规则外变化、缺件或模式不明则停止并补准确范围。

### 3.2 完整候选与单次原子提交

F1私有候选包含两处结构、真实correction及必要元数据的全部字节和完整差异。元数据时间是本次候选准备时真实采集的带时区时间，另记实际写入尝试／读回时间，不伪称它是写后成功时刻；correction的verification明确“写前检查已具证、写后仍待证”，不能预填写后通过。

形成F1及等待人工批准均在源锁外。提交时原`registry_lock`覆盖重读、原值校验、以冻结参数在内存重现候选、严格校验、fsync、单次原子替换和读回。重现字节必须与F1全候选hash完全一致；漂移不修改F1重发，不嵌套普通apply、不关锁／抢锁。例外回执如实标注`exception`产生机制；普通started和结束回执仍由普通工具产生。

事务记录仍为原六字段；B的`request_sha256`填完整例外意图摘要，`base_sha256`填真实原hash。自身correction的scope／summary／evidence指明本合同ID、一次性例外产生机制和真实证据路径；保留原事件最小字段及单行纯文本限制，不把含管道的JSON请求塞入表格或事件单元。

F1候选可以指向固定的未来回执路径，但不写未来回执hash或声称它已存在。替换后记录实际结果；失败／未知只读核对，不回滚覆盖、换ID或自动第二次提交。

## 4. 证据依赖必须无环

准确依赖顺序为：R3冻结包→实际机制／模板／普通setup请求→F0清单→前置授权→普通setup证据→post-setup保护／治理输入→最终请求→两种摘要→私有候选／差异→F1清单→外部提交门／必要后置批准→实际例外回执。

不得把自己的原件hash／意图摘要、候选完整after hash、F1清单／后置提交门／写后回执hash放入最终请求；不得让上游引用原件反向包含下游最终hash。固定路径或ID可提前命名，未来hash和实际结果不能预造。脚本不把自己的最终hash嵌入自身；其hash由外部清单绑定。完整after hash只能在候选含事务摘要后计算，随后置于F1／写后证据，不回填请求或候选自身。

## 5. 按阶段判断占用和停止

源README在各阶段都必须已存在且真实、非链接；这不是“路径占用错误”。setup前新任务／事务ID须未使用；setup后自身行应存在，须核同一owner／空grants及原行hash。已确认的本任务证据仅按hash读取或排他新建其他文件，不能覆盖；外来／身份不明占用、链接、hash失配、新文件冲突或新事务ID已用即停。

F0到F1只允许已确认自身setup的差异；不能把其他写入冒充setup，也不自动重基。F1冻结后任一整册／局部／归属／输入漂移、授权或新鲜治理缺失，停止B提交；不能沿普通§5.5悄悄替换F1。A的普通事务仍按其既有有界漂移规则。
