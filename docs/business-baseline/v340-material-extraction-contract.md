# V3.4.0离线材料提取合同（D0冻结，尚未实现）

版本：`v340-extraction-1`。冻结于2026-10-24，依据2026-10-23 D0计划及本地候选实测。**这是D1目标合同，不是当前代码能力声明；PDF/DOCX部署及完整限额执行仍BLOCKED。** 当前生产准备入口继续只收.md/.txt，来源全部禁用。

## 1. 输入与支持范围

共同表单、14节点/136输入ID、顺序及文件/文本/配置边界不变；一个普通`*_file`对应一份明确文件。扩展名只作白名单，必须同时校验实际PDF头/文档结构或DOCX ZIP/Content-Types/主文档关系，拒绝MIME与内容不符、普通ZIP改名或嵌套容器伪装；mediaType由Host核对，不信任调用方声明。`upstream_md_file`继续为一份实际累计Markdown，不接受PDF/DOCX，不扫描旧稿。`user_input`保持用户手动指令；文件和同语义文本同时提供时保留两份证据，不互相替换。

第一切片只接受以下完整可检测子集；出现子集外内容为UNSUPPORTED_PROFILE，不能丢掉其内容后伪装accepted：

- PDF：可读取文字层、无加密、无扫描/图像语义、无附件/表单/注释/活动动作、可支持字体映射的简单正文；逐页有可审计文字。空页、混合扫描、图片、公式/矢量技术图、多栏顺序无法保证等须明确不支持或另做后续格式切片。纯装饰与技术图难以可靠区分时拒绝该文件，不猜测其语义。
- DOCX：主`word/document.xml`中普通段落及未合并、非嵌套表格，按正文块/行/单元格/段落顺序。预检识别非空页眉/页脚、脚注/尾注、批注、插入/删除修订、文本框、字段、超链接、绘图/公式/嵌入对象、宏及外部关系；本切片一律明确不支持，不靠Document.paragraphs跳过。**实际生效的自动编号/项目符号同样拒绝，不能丢掉编号再提交正文**，具体规则见下节。仅作为正常模板声明且未生效的样式/主题/编号数据可以保留，但不能执行其外部关系；预览缩略图等元数据不得被当作材料正文。

这里的完整只指已声明且经过预检的文字子集，不保证阅读版式、图片语义或专业内容完整。无法可靠判定是否在子集内也必须拒绝，不能因extract_text返回非空便宣称完整。真实专业质量继续未评估。压缩包、图片/OCR及新增导出格式仍在后续清单。

### 1.1 DOCX编号拒绝策略：v340-docx-numbering-policy-1

2026-10-24按用户明确决定补修D0-R1。首切片不展开、不补造自动编号；任何正文或表格段落的**有效numId非零**均为`V340_EXTRACTION_UNSUPPORTED_PROFILE`。即使显示标签为空/未知、正文已经手写“1.”，也不能用可见文本代替编号状态判断。

- 按当前段落直接pPr/numPr、所用段落样式及basedOn链、未显式指定样式时的默认段落样式、docDefaults解析属性。numId与ilvl按属性继承，不能把“段落只写ilvl”当成没有编号。样式链缺失、循环、值非法或无法确定时拒绝，不默认为普通段落。
- 默认段落样式的`w:default`按合法布尔值统一判定：`1/true/on`等价为真，`0/false/off`等价为假，缺省属性不标记默认；空值/非法值及多个真值默认段落样式拒绝，不静默当假。假值仅表示该样式不会被隐式选为默认；正文显式pStyle使用其非零numId仍拒绝。三种真值下，段落或叶样式的显式numId=0均仍可取消继承。2026-10-24 D0-NUM-R1修复只是落实原默认样式合同，不启用DOCX或迁移历史证据。
- 数字编号、项目符号、起点/重启、lvlOverride/startOverride、多级及编号样式链接，只要有效numId非零都拒绝，不因标签格式或当前层级不同放行。先发现首个生效或无法解析段落即拒绝整份所选文件，不发布部分提取正文/prepared，不消耗额度或调用模型；原输入/草稿保持，用户可明确改用手写编号文本或移除材料。
- 正确处理显式`numId=0`取消继承：段落直接属性优先于样式，叶样式属性优先于basedOn基样式，不能用“XML中出现numPr/numbering.xml”作为一律拒绝条件。仍须能解析实际使用链；其它profile条件继续独立检查。
- 手写编号本身是原文，不能删除、改写或通过正则“识别为自动编号”。未被正文引用的num/abstractNum、重启/多级定义、编号样式及其未使用链不构成生效编号。保留这些对照只表示通过编号检查，不表示DOCX其它内容已支持。
- 编号策略及上述解析/拒绝规则必须进入policySHA256，实际D1预检适配器代码进入adapterSHA256；不得沿用旧的未检查编号策略确认。禁止改变rawSHA256/textSHA256的含义来掩盖编号丢失。

独立离线候选为`scripts/check-v340-docx-numbering.py`：有界stdin输入、标准库ZIP/XML，只输出body-free编号资格结果。`reject`表示生效或无法解析，`eligible`仅表示未发现生效编号，其它格式/关系/完整性/资源条件仍由D1验证；该脚本不是全文DOCX验证器、提取器或Host入口，没有接入生产，也不证明D1硬内存/时间等保护已实现。原19项正式回归见业务包`test/v340-docx-numbering-policy.test.mjs`，默认布尔新增20项见`test/v340-docx-default-boolean.test.mjs`，合计39项及各自固定二进制夹具；原19项和旧夹具原字节保留。

## 2. 字节读取及权限

Host按权威Workspace读取明确相对路径。先绑定根、父目录及最终文件身份，再有界读取原始字节；读取前/后及返回确认前复核。目录重定向、A→B→A、同hash跨项目、同inode但换根、原地变更/增长都不能被hash替代权限。旧B检查脚本的强读取合同仅作参考，不能假定现有workspace-materials已经穷尽这些窗口。

解析器只收到已接受的原始字节及固定策略，禁止接收用户任意路径或自行打开源路径；通过受限stdin/内存传输。检查和解析必须针对同一份字节，不重新扫描或猜最新文件。所有成功、失败、超时、取消释放句柄/子进程；进程只处理本次材料，不读取凭据、Profile或用户其它文件，不执行宏/脚本或加载外部资源。

原文件留在用户项目，既不改名/覆盖，也不把完整二进制复制进运行JSON。一次准备期间保留原字节完成hash/提取；运行冻结保存提取全文和证据，重开/派发只用冻结内容。旧原文件后来变化或删除不能改写历史快照；新确认/新准备必须重新核对当前所选文件和Workspace身份。

## 3. 文本归一化及定位

所有文本必须是有效Unicode，不含NUL或孤立代理项。只做CRLF/CR→LF；PDF每页去掉提取器返回的末尾LF，DOCX段落保持原文本。各页/段落/单元格段落用一个LF连接，不做其它trim、空白折叠、NFC/NFKC、纠错、拼写补充或模型补文；无可用文字返回失败，不输出空串成功。

定位单位为**UTF-16码元**，start含、end不含，均相对归一化后的完整body。拼接LF由策略确定，可位于片段之间；各片段严格有序、不重叠、不越界、不切开代理对，片段与分隔LF必须覆盖全文，不允许以定位字段掩盖丢文。

- PDF定位：`{kind:'pdf-page',page:1}`，page从1开始，不声称提供字符坐标或还原布局。
- DOCX普通段落：`{kind:'docx-paragraph',part:'word/document.xml',block:1}`。
- DOCX表格段落：`{kind:'docx-cell-paragraph',part:'word/document.xml',block:2,row:2,cell:2,paragraph:1}`；block按主正文w:p/w:tbl顺序从1计，行/单元格/段落均从1计。不推算DOCX页码。

## 4. hash、字段归属与确认

新文件值保持`{filename,body,sha256}`原义，`sha256=SHA256(UTF8(body))`；只增加有版本的Host证据`extraction`。不把它改成PDF/DOCX原hash。

`extraction`严格字段：

```text
version: 'v340-extraction-1'
source: { workspaceId, relativePath, mediaType, bytes, rawSHA256 }
text: { utf16Length, utf8Bytes, textSHA256 }
parser: { name, version, runtimeVersion, componentTreeSHA256, runtimeSHA256, adapterSHA256 }
policySHA256
coverage: 'declared-text-profile'
locations: [{ locator, startUTF16, endUTF16 }]
```

source.relativePath使用现有安全相对路径规范，与本次draft.filePaths精确关联；不放绝对路径/凭据。parser指纹绑定实际将运行的产品解释器、完整依赖闭包及适配脚本adapterSHA256，不能填本次Codex元数据冒充已部署。text.textSHA256必须等于外层sha256，bytes/长度与实际字节和全文一致。componentTree指纹规则及文件集合与批准分发清单一起固定；本轮候选树指纹算法见[候选核对](v340-material-extraction-candidates.md)。

新receipts仍以`sha256`绑定模型所见正文，并增加`extractionSHA256=SHA256(UTF8(canonicalJson(extraction)))`。inputHash继续绑定节点与完整receipts；输入快照总hash绑定完整values。原文件字节、相对路径、Workspace、提取正文、定位、解析器、策略任一变化均使新确认失效，即使提取文本相同也不能沿用确认。观测时间、耗时、PID/RSS只进诊断记录，不参与确定性提取证据，避免同字节重复prepare凭空失效。

只有Host材料准备能产生extraction；浏览器/RPC仍只收路径/文本/配置，不接受外部自填extraction。模型更新引用user_file时仍用textSHA及正文定位；rawSHA只作原件追溯，不作为可读正文或访问凭证。

## 5. 内部编码和历史兼容

这是拟定的显式新分支，D1前不得将额外字段塞入旧严格schema：

1. 共同业务表单inputSchemaVersion仍`v340-1`，字段ID和两来源表单不分叉；材料证据版本独立为`v340-extraction-1`。
2. 带提取证据的新inputSnapshot标`materialEncoding:'extracted-text-v1'`；该标记与values中extraction或上游文稿v2的非空材料证据同时存在，缺标记、空标记或不相符组合均拒绝；旧无标记路径原样保留。完整或values-v1中都保留唯一完整extraction，重建只用冻结values，不重读文件或再次解析；计入原2MiB限制。
3. 新提取材料或继承新版材料证据的原生候选使用`v340-native-candidate-3`，与新materialEncoding互相匹配，绑定新增材料/策略和请求摘要；v1/v2旧prompt、序列化和摘要验证路径保留且不得携带新提取字段，只读旧记录不能触发重签或新调用。无新材料证据的原有路径不自动改为v3。
4. 累计主Markdown使用显式`oasis-v340-2`结构快照承接非空`material_extractions`；每条为`{workflow_run_uid,input_id,extraction}`，按节点历史保留并计入1MiB文稿上限。新读取器同时严格读旧v1及新v2；新生成继承v2时保留全部证据，人工编辑不得改写它。旧v1生成/修订不自动升级；旧文件/回执/审核hash不变。
5. 旧安装包读取新材料编码/新文稿不保证兼容，须列升级/回退限制及阶段6验收；不通过删字段、重算旧hash或把unknown重派“解决”降级。

上述v3/v2名称是待实现合同，当前代码未增加这些能力。专业API来源保持禁用，新证据不自动证明API接受原二进制或提取文本；逐节点API映射仍留E，不能静默改变上传格式。

从用户明确选择的上游文稿继承材料证据，只证明该文稿声明的历史来源及当前文件结构/hash，不证明当前Host又读取了原二进制。新下游须保留“历史材料原件未重新核验”的警示，不将原件hash提升为已核验事实/权限，也不得按证据中的旧路径另读其它项目。手工伪造结构自洽文稿同样不能绕过此边界。

## 6. 固定容量政策与尚未验证的执行机制

以下为本切片冻结的**目标准入上限**，不是当前产品已实现保证。保守拒绝优先于截断/丢证据；D1必须通过实际边界回归及机制核对后才可启用。除现有上限和下述pypdf分支外，所有新上限尚未做最大恶意输入/平台机制验收，故D1仍BLOCKED。

## 7. 状态、失败和保全

未提供仍not_provided；已接受文字但专业语义未评估仍保留原warning规则，不新增必填。对于用户实际选中的损坏、加密、子集外、超限或解析不可用文件，不发布部分prepared/正文，不自动删除材料、转空值或发起生成；用户明确移除或更换后可按原缺失警示规则继续。warning不等于完整提取。

新增内部失败分类建议冻结为`V340_EXTRACTION_UNAVAILABLE`、`V340_EXTRACTION_UNSUPPORTED_PROFILE`、`V340_EXTRACTION_LIMIT`、`V340_EXTRACTION_FAILED`；文件身份变化沿用材料变化类错误。对外只暴露固定安全说明，不泄露原文、路径、堆栈或子进程stderr。新失败不得清掉原草稿、审核结果、运行、unknown或已保存文件；未完整准备不得消耗候选额度或触发流接口。source.enabled/dispatchEnabled/realCallVerified继续false。
