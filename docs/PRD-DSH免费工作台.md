## 1. 产品概述

### 1.1 产品定义

绿洲慧写 DSH 免费工作台是一套安装在 DSH 上的专业工作预设：

```text
绿洲 DSH Profile
├─ DSH 原生项目、文件、会话和通用 Agent
├─ 绿洲专业 Skills
└─ 绿洲专业服务 Plugin
   ├─ 账户与凭据
   ├─ 专业能力目录
   ├─ 报价与付费确认
   ├─ 文件上传和隐私确认
   ├─ 任务与进度
   ├─ 结果渲染和本地写回
   └─ 产物血缘与人工门禁
```

### 1.2 产品定位

> 免费管理本地研发与专利项目，在需要专业交付物时，以透明的 ¥1/¥3/¥5 单次价格调用绿洲专业能力。

### 1.3 产品原则

1. **不重复制造工作台**：优先使用 DSH 原生项目、文件、会话、工具和 Agent。
2. **免费入口、付费结果**：安装、通用能力和本地操作免费；服务端专业工作流按成功次数收费。
3. **服务端专业资产**：Skill 负责发现和编排，核心专业逻辑保存在 Dify。
4. **显式授权**：付费、上传、人工门和对外操作均需要用户确认。
5. **结果是文件资产**：专业结果必须写回项目，而不是只停留在聊天消息中。
6. **失败不收费**：技术失败、合同失败、预检阻断和执行前取消不结算。
7. **版本可追溯**：能力、价格、输入、输出和父产物都有版本和来源。
8. **适配变化**：隔离 DSH 开发者预览阶段的兼容风险。
9. **固定按次总价**：Dify Token、模型和标准运行成本由平台内部承担，用户报价与账单只出现服务费。

DSH 官方将模型、工具、Skills、会话、存储和 UI 等能力设计为插件，并声明开发者预览阶段可能发生兼容性破坏：[DSH 产品说明](https://deepseek.com/harness/en/)、[DSH GitHub](https://github.com/deepseek-ai/deepseek-harness)。

## 2. 用户与核心场景

### 2.1 用户 A：技术开发人员

**需要完成的工作**：

- 在本地项目中整理研发材料；
- 调用技术背景研究或 TRIZ；
- 将分析结果继续转换为交底书或专利初检；
- 通过 API 或 Agent 工具自动化重复任务；
- 在 DSH 通用 Agent 中自行配置模型；该本地设置不改变 Dify 专业服务的固定价格。

### 2.2 用户 B：专利代理人

**需要完成的工作**：

- 建立案件工作区并维护材料版本；
- 按节点生成或检查专利文档；
- 选择经确认的权利要求书、说明书进入全文复检；
- 查看来源、风险、缺口和待确认事项；
- 将人工决定记录为下一节点的权威输入。

### 2.3 管理角色

首版只定义接口，不在插件内实现复杂管理后台：

- 商业平台运营人员：能力上架、下架、价格和版本；
- 财务/客服：账单、退款和异常处理；
- 专业质量负责人：工作流验收、质量事件、版本暂停；
- 开发运维：API 网关、Dify 映射和可观测性。

## 3. 目标与非目标

### 3.1 P0 产品目标

1. 用户能够安装绿洲 Profile/Plugin，并继续使用 DSH 原生通用工作台。
2. 用户能够通过浏览器完成商业平台账户授权，令牌安全保存。
3. 插件能够展示服务端专业能力、版本、价格、输入和限制。
4. 用户能够在明确报价和上传清单后创建专业任务。
5. 插件能够展示异步进度、失败原因、余额变化和结果状态。
6. 合同有效的结果能够安全写回本地项目并带有来源元数据。
7. 任务不会重复扣费；失败任务自动释放余额或退款。
8. 首发支持 1-1、2-6、1-2 三个工作流。
9. 标准 Dify 专业任务只向用户收取能力目录公布的 ¥1/¥3/¥5 服务费；模型 Token 和标准运行成本只在服务端内部核算。

### 3.2 非目标

- 不实现 DSH 核心、模型层、通用 Agent、项目树或文件编辑器；
- 不复制绿洲前端 3.0 的完整 React SPA；
- 不让客户端直接调用 Dify；
- 不在 P0 实现团队、发票、复杂套餐和企业管理；
- 不在 P0 自动编排完整 14 节点无人值守链；
- 不自动提交专利申请、发送法律文件或执行不可逆外部操作；
- 不把 AI 输出宣传为最终法律结论；
- 不向用户拆分收取 Dify Token、模型、检索或其他标准运行附加费。

## 5. 产品架构与组件边界

### 5.1 组件

以下名称为工作名称，实施时可根据 DSH 打包规范调整，但职责不得混合：

| 组件 | 工作名称 | 职责 |
|---|---|---|
| DSH Profile | `oasis-professional-profile` | 声明兼容 DSH 版本、默认插件和 Skill 组合 |
| Host Plugin | `oasis-professional-service` | 注册服务、工具、事件，调用商业平台 API |
| Client Extension | `oasis-professional-service/client` | 设置卡片、报价确认、任务卡片和产物操作 UI |
| Skill Bundle | `oasis-patent-skills` | 任务识别、输入准备、工具使用规则和人审提示 |
| API Adapter | 商业平台 `/v1` | 向插件和开发者提供稳定合同，适配旧接口与 Dify |
| Cost Ledger/Budget Guard | 商业平台内部组件 | 记录每任务模型、Token、工具和人民币成本，执行版本预算与暂停门禁，不向客户端计费 |
| Dify Workflows | 已有专业工作流 | 执行 TRIZ、检索、撰写、检查等核心逻辑 |

### 5.2 不迁移旧 SPA 的原因

旧前端已有 React、Router、Zustand、Tailwind、项目/会话/文件/聊天等完整工作台。直接嵌入 DSH 会造成：

- 两套项目和会话模型；
- 两套文件状态与恢复逻辑；
- 两套路由、认证和全局状态；
- DSH 版本升级时更大的兼容面积；
- 插件体积和维护成本显著增加。

因此只复用：

- API Schema 和类型；
- 文件输入归一化；
- 异步任务状态机；
- 超时、错误和结果归一化；
- Markdown/Mermaid/KaTeX/下载安全处理；
- 余额、流水、消费和退款模型；
- 现有测试与安全校验思路。

## 6. 信息架构与入口

### 6.1 DSH 内入口

1. **专业能力工具/命令**：由 Agent 根据 Skill 选择，也允许用户主动打开。
2. **设置卡片**：账户、服务地址、隐私、保留期和兼容状态。
3. **任务卡片**：报价、进度、错误、余额和结果操作。
4. **专业能力面板**：筛选 Basic/Fast/Pro、节点、可用状态和输入类型。
5. **产物操作**：预览、写回、另存、打开来源、作为下一节点输入。

### 6.2 设置卡片

| 字段 | 说明 | P0 行为 |
|---|---|---|
| 服务端地址 | 生产地址默认只读；开发环境可切换 | 切换时清除不兼容令牌并二次确认 |
| 账户状态 | 未连接/已连接/已过期 | 支持连接和登出 |
| 用户标识 | 脱敏手机号或账户名 | 不显示敏感详情 |
| 余额 | 当前可用余额 | 可跳转 Web 充值，不在插件嵌支付页 |
| 数据保留 | 服务端默认保留期 | 展示并链接到政策 |
| 上传确认 | 始终确认 | P0 不允许永久关闭 |
| 插件版本 | Plugin/Profile/DSH 版本 | 显示兼容性和升级建议 |

### 6.3 能力卡片

每张卡片必须显示：

- 节点编号和名称；
- Basic/Fast/Pro；
- 当前单价；
- 能力版本；
- `available / beta / coming_soon / suspended`；
- 必需输入和产物；
- 是否异步；
- 是否需要人工门；
- 专业限制和“不构成最终法律意见”等说明；
- 上次目录更新时间。

客户端不得通过节点编号自行推算价格。

## 7. P0 用户流程

### 7.1 安装与账户连接

1. 用户安装兼容版本的 DSH。
2. 安装绿洲 Profile/Plugin；系统显示来源、版本和权限。
3. 插件检查 DSH 兼容范围。
4. 用户点击“连接绿洲账户”。
5. 插件请求设备码，显示验证码和验证地址。
6. 用户在浏览器登录现有商业平台并确认设备。
7. 插件轮询令牌，成功后写入 DSH 凭据机制。
8. 插件获取用户摘要、余额和能力目录。
9. 授权失败、过期或取消时，不保存半成品凭据。

### 7.2 单个专业任务

1. 用户在本地项目提出任务，或主动选择专业能力。
2. Skill 判断任务并调用“获取能力详情”。
3. 插件读取当前项目中的候选输入，但不上传。
4. 免费预检检查必填项、文件类型、大小、人工门和余额。
5. 商业平台生成报价；插件展示：
   - 能力和版本；
   - Basic/Fast/Pro 与 ¥1/¥3/¥5；
   - 唯一应付服务费，并明确已包含 Dify Token、模型和标准运行成本；
   - 将上传的文件；
   - 服务端数据用途和保留期；
   - 预期主产物和限制。
6. 用户明确确认。
7. 插件上传必要文件并提交带 `idempotency_key` 的任务。
8. 商业平台冻结余额并调用对应 Dify 版本。
9. 插件显示任务进度，允许用户取消。
10. 商业平台校验输出合同；成功后结算。
11. 插件显示主 Markdown、附件、状态、来源、风险和账单。
12. 用户确认写回位置，或采用已预览的默认位置。
13. 插件写回文件及本地元数据，不覆盖已有同名文件。

### 7.3 人工门任务

以 3-8 为例：

1. 插件发现目标能力要求“经用户确认的权利要求书和说明书版本”。
2. 从本地血缘记录列出候选文件及版本。
3. 用户逐一选择并确认。
4. 插件记录确认时间、文件哈希和用户动作。
5. 只有人工门满足后才允许生成报价和付费任务。
6. 人工门未满足时返回 `blocked_precheck`，不冻结、不扣费。

### 7.4 失败与退款

1. 任务进入失败状态时，插件显示错误类别而不是原始服务端堆栈。
2. 商业平台自动释放冻结余额或创建退款流水。
3. 插件轮询到账务终态后显示“未收费”或“已退款”。
4. 技术失败可以在同一个 `idempotency_key` 下安全恢复；不能重复冻结。
5. 若用户改变关键输入，必须生成新报价和新任务。

## 8. 功能需求

### 8.1 授权与凭据

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| AUTH-01 | 支持设备码授权，不要求在 DSH 中输入密码 | P0 | 浏览器确认后获得短期访问令牌和刷新令牌 |
| AUTH-02 | 令牌保存在 DSH 凭据机制，不写入普通配置、日志或项目 | P0 | 扫描配置和日志无明文令牌 |
| AUTH-03 | 支持刷新、过期、撤销和登出 | P0 | 401 只触发一次安全刷新；失败后要求重连 |
| AUTH-04 | 服务端地址切换必须清除不匹配的令牌 | P0 | 生产令牌不可发送到测试地址 |
| AUTH-05 | Dify 和第三方数据源密钥永不下发客户端 | P0 | 抓包、日志和 API 响应中不存在相关字段 |

### 8.2 服务端成本治理

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| COST-01 | 标准任务的用户报价只包含 `service_fee` | P0 | 不返回 Token、模型、外部运行费用字段或其他附加费 |
| COST-02 | 服务端记录每任务模型、输入/输出 Token、工具调用、运行时间和人民币成本 | P0 | 成本记录关联 `job_id` 和能力版本，仅内部可见 |
| COST-03 | 每个能力版本设置模型白名单、最大 Token、最大重试、超时和并发预算 | P0 | 超预算请求被服务端阻断或安全降级，不向用户补收费用 |
| COST-04 | 监控成功任务 P50/P95 成本、失败成本和退款成本 | P0 | 可按能力版本查询趋势和告警 |
| COST-05 | P95 成功任务可变成本达到或超过售价时禁止正式发布 | P0 | Alpha 可测试，但能力不得进入 `available` |
| COST-06 | 成本超过30%经营目标时触发优化或版本复审 | P0 | 不采用用户 Token 透传或已确认任务补价 |
| COST-07 | DSH 本地通用 Agent 模型设置不参与 Dify 计费 | P0 | 插件不读取本地模型 Key，Dify 报价不因其变化 |
| COST-08 | 平台 Dify、模型和数据源密钥只存服务端 | P0 | 抓包、日志和客户端响应无明文密钥 |

### 8.3 能力目录

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| CAT-01 | 从服务端获取能力目录 | P0 | 含价格、版本、状态、Schema、产物、限制 |
| CAT-02 | 本地缓存最后一次成功目录 | P0 | 离线时只允许查看，不允许按旧价格创建任务 |
| CAT-03 | 能力暂停时禁止新任务 | P0 | 已运行任务仍可查询和取回结果 |
| CAT-04 | 客户端不得推算或修改价格 | P0 | 报价与目录均由服务端签发 |
| CAT-05 | “即将上线”能力不能触发付费 | P0 | 1-4、3-8、3-9、4-12 默认不可执行 |

### 8.4 报价与确认

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| QUOTE-01 | 执行前创建服务端报价 | P0 | 报价包含能力、版本、费用、有效期和余额 |
| QUOTE-02 | 标准报价只有固定 `service_fee` | P0 | `total = service_fee`，无 Token、模型或运行附加费 |
| QUOTE-03 | 展示上传清单、用途和保留期 | P0 | 未确认不能上传或创建任务 |
| QUOTE-04 | 报价过期后必须重新请求 | P0 | 不能使用过期报价 |
| QUOTE-05 | 价格或版本变化时要求重新确认 | P0 | 不静默替换用户已确认报价 |

### 8.5 文件处理

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FILE-01 | 支持文本、Markdown、DOCX、PDF和能力声明的图片类型 | P0 | 以服务端 Schema 为准 |

## 10. 商业平台 `/v1` API 合同

### 10.1 设计原则

- `/v1` 是 DSH 和外部开发者的稳定门面；
- 旧 `/apicategories/*` 和 `/user/*` 接口由服务端适配，不直接暴露为插件内部模型；

## 11. 状态模型

### 11.1 任务状态 `job_status`

```text
draft
→ awaiting_confirmation
→ queued
→ running
→ awaiting_human
→ validating
→ completed

任意执行态 → cancel_requested → cancelled
任意执行态 → failed
```

### 11.2 账务状态 `billing_status`

```text
not_applicable
→ quoted
→ reserved
→ settled

reserved → released
settled  → refund_pending → refunded
```

### 11.3 内容状态 `content_status`

沿用 14 节点主 Markdown 合同：

- `ready`：合同完成，可进入人工审核或下游；
- `warning`：合同完成但存在已披露的非阻断风险；
- `blocked`：关键材料或确认缺失，不得继续正式结论链。

三个状态维度不得合并。例如：

| 场景 | `job_status` | `billing_status` | `content_status` |
|---|---|---|---|
| 正常完成 | `completed` | `settled` | `ready` |
| 有披露风险但交付完整 | `completed` | `settled` | `warning` |
| 免费预检缺材料 | 不创建任务 | `not_applicable` | `blocked` |
| Dify 技术失败 | `failed` | `released` | `null` |
| 输出合同缺失 | `failed` | `released` | `null` |
| 已结算后确认质量事故 | `completed` | `refunded` | 原状态保留并标记质量事件 |

### 12.1 默认目录建议

插件只在用户确认的项目根目录内写入。建议结构：

```text
项目根目录/

│  ├─ 1-2-triz_analysis_report_patent.md
```

- 不覆盖用户已有文件；
- 同名产物按节点和版本隔离；
- 隐藏元数据不承载用户唯一可读结果；
- 删除元数据不会破坏主 Markdown 本身的可读性。

### 12.3 写回规则

1. 先下载到临时文件并校验大小、类型和哈希；
2. 预览目标绝对路径；
3. 若目标不存在，原子写入；
4. 若目标存在，生成新版本名或要求用户选择，禁止静默覆盖；
5. 主文件成功后再写元数据；
6. 写回失败不改变服务端已完成任务，但插件必须支持重新下载；
7. 不把服务端 URL 当作永久项目资产，最终结果必须落地或明确保持远程状态。

## 14. 隐私、安全与权限

### 14.1 数据分层

| 数据 | 默认位置 | 上传条件 |
|---|---|---|
| 项目原始文件 | 用户本地 | 被能力声明为必需且用户确认 |
| DSH 通用 Agent 模型 Key | DSH 凭据/用户环境 | 绿洲插件永不读取或上传 |
| 商业平台令牌 | DSH 凭据 | 仅发送到匹配的商业平台域名 |
| Dify/模型/数据源密钥 | 商业平台服务端 | 平台统一管理，永不下发 |
| 任务元数据 | 本地 + 商业平台 | 最小化，不在账单中复制正文 |
| 专业输入与结果 | 任务需要时服务端处理 | 按展示的保留策略处理 |

DSH 默认在本地处理输入、输出、附件和运行记录；调用外部插件或服务可能上传数据。因此插件不能用“DSH 本地优先”暗示专业 API 调用仍完全本地：[DSH 数据处理说明](https://www.deepseek.com/harness/en/data-processing/)。

DSH 本地通用 Agent Key 只服务本地通用 Agent，绿洲插件不得读取或同步。Dify 专业工作流使用平台服务端统一管理的模型凭据，其内部 Token 成本不会进入用户报价或账单。

### 14.1.1 服务端内容保留

- 个人版 P0 的上传输入和生成产物默认保留 7 天；
- 用户可提前删除服务端正文和附件，本地已写回文件不受影响；
- 到期删除正文和附件，账务、任务状态、版本、金额、时间和脱敏哈希按适用政策保留；
- 企业版不同期限必须在能力目录和报价中明确显示；
- 备份清理周期、删除证明和法律保留例外在 Beta 前完成合规审查。

### 14.2 安全要求

- 生产只允许 HTTPS；
- 访问令牌短期有效，刷新令牌可撤销；
- 设备码短期有效且只能使用一次；
- API 响应和日志统一秘密字段过滤；
- 所有下载内容经过类型、大小和安全处理；
- Markdown 使用白名单渲染，禁止任意 HTML/脚本；
- 外链和下载显示来源；
- 插件声明最小权限；
- 只安装已签名或来自受控仓库的版本；
- 高影响操作必须人工确认。

DSH 官方安全政策强调仅安装可信且经过审查的插件/Skills，并对重大变更保留人工确认：[DSH 安全使用政策](https://www.deepseek.com/harness/en/privacy/)。

### 14.3 密钥验收

以下位置不得出现明文 Dify、数据源或商业平台刷新令牌：

- 插件普通配置；
- 项目文件和 `.oasis-professional` 元数据；
- 浏览器控制台；
- 网络错误消息；
- DSH 会话消息；
- 服务端普通应用日志；
- `/v1/capabilities`、报价、任务和产物响应。

Dify 官方文档建议 API Key 保存于后端而非客户端：[Dify API 文档](https://docs.dify.ai/api-reference/%E6%96%87%E6%A1%A3%E5%9D%97/%E5%88%A0%E9%99%A4%E6%96%87%E6%A1%A3%E4%B8%AD%E7%9A%84%E5%9D%97)。

## 15. 错误模型与恢复

### 15.1 错误代码

| 类别 | 示例代码 | 用户动作 | 是否收费 |
|---|---|---|---|
| 输入 | `INPUT_MISSING`、`FILE_UNSUPPORTED` | 补充或更换文件 | 否 |
| 人工门 | `HUMAN_GATE_REQUIRED` | 选择并确认版本 | 否 |
| 认证 | `AUTH_EXPIRED`、`AUTH_REVOKED` | 重新连接账户 | 否 |
| 余额 | `INSUFFICIENT_BALANCE` | Web 充值后重试报价 | 否 |
| 价格 | `QUOTE_EXPIRED`、`PRICE_CHANGED` | 重新查看并确认 | 否 |
| 任务 | `JOB_NOT_FOUND`、`JOB_CONFLICT` | 查询原幂等任务或联系支持 | 视原任务 |
| 技术 | `UPSTREAM_TIMEOUT`、`DIFY_FAILED` | 安全恢复或稍后重试 | 否 |
| 合同 | `OUTPUT_CONTRACT_FAILED` | 等待平台修复 | 否 |
| 质量 | `QUALITY_INCIDENT` | 查看通知和退款状态 | 已结算则退款 |

### 15.2 重试规则

- GET 查询允许指数退避和抖动；
- 文件上传只重试未成功的分片或文件；
- POST `/v1/jobs` 超时后先按 `idempotency_key` 查询，不盲目再次创建；
- Dify 工作流不得由客户端自动重复执行；
- 用户改变关键输入时创建新的报价和幂等键；
- 服务端返回不可重试错误时，插件停止并给出具体动作。

### 15.3 DSH 重启恢复

启动时：

1. 读取本地未完成任务索引；
2. 使用账户令牌查询服务端真实状态；
3. 服务端状态优先，保留本地最后观察时间；
4. 对已完成但未写回的任务提供“恢复下载”；
5. 对已退款任务更新本地账务展示；
6. 不自动继续需要人工确认的任务。

## 16. 非功能需求

### 16.1 可用性

- 目录或余额服务短时失败不影响 DSH 本地通用功能；
- 离线时可查看本地产物和最后目录，但不能创建付费任务；
- 插件故障不得阻止用户打开和编辑已有项目文件；
- 每个错误至少提供一个可操作的下一步。

### 16.2 性能目标

以下目标在指定网络和测试环境中测量，不作为当前已达事实：

| 指标 | Alpha 目标 |
|---|---:|
| 缓存命中时打开能力面板 | P95 < 500 ms |
| 正常网络下获取目录 | P95 < 2 s |
| 创建报价 | P95 < 2 s，不含文件上传 |
| 服务端进度到插件可见延迟 | P95 < 5 s |
| 已完成产物开始下载 | P95 < 3 s，不含实际传输时间 |

Dify 长任务的总执行时长按能力单独建立基线，不用统一前端超时判断失败。

### 16.3 可访问性与交互

- 目标符合 WCAG 2.2 AA；
- 所有确认、取消、重试和下载可键盘操作；
- 价格、状态和错误不能只靠颜色表达；
- 进度有文本说明；
- 屏幕阅读器能读取能力名称、价格和风险；
- 高风险确认按钮文案说明后果，不能只写“确定”。

### 16.4 兼容与升级

- Profile 声明 DSH 最小和最大已验证版本；
- 不在范围内时显示阻断或风险提示，不静默继续；
- DSH 适配代码集中在单一层；
- 商业业务服务不直接依赖 DSH 内部 UI 对象；
- 插件升级前可导出本地任务索引；
- 旧能力版本退役后历史产物仍可打开。

## 18. 验收测试

### 18.1 静态与合同测试

- 能力 Manifest Schema 校验；
- Basic/Fast/Pro 仅允许 1/3/5 元；
- 价格版本和工作流版本必填；
- 主 Markdown 八章节检查；
- 1-3 与 3-8 同名产物隔离；
- 人工门声明和预检规则检查；
- API OpenAPI/Spectral 校验；
- 旧接口适配合同测试；
- 密钥和秘密字段扫描。

### 18.2 Dify 运行测试

每个 P0 能力至少 3 组：

1. 完整正常输入；
2. 边界或部分可选输入；
3. 缺失关键输入或预期阻断。

验证内容：

- 实际导入、发布和运行；
- workflow run 和节点执行证据；
- 主产物名称和内容合同；
- `ready/warning/blocked` 的真实性；
- 模型、输入/输出 Token、执行时间、工具调用和人民币可变成本；
- 失败是否能安全重试；
- 输出是否适合作为下游输入。

### 18.3 商业平台测试

- 三档价格分别报价、冻结和结算；
- 余额不足；
- 报价过期和价格变化；
- 同一幂等键并发请求；
- 创建请求超时后的状态恢复；
- 技术失败释放余额；
- 已结算任务退款；
- 账单、任务、报价三向追溯；
- 暂停能力后禁止新任务；
- 标准报价只含 `service_fee`，且 `total = service_fee`；
- 内部 Token、模型和运行成本不出现在客户端响应或账单。

### 18.4 DSH 插件测试

- 安装和版本不兼容提示；
- 设备码授权、刷新、撤销和登出；
- 目录、报价、上传确认和余额；
- 异步进度、取消、重启恢复；
- 结果预览、下载和不覆盖写回；
- 离线查看本地产物；
- 键盘和屏幕阅读器基本流程；
- 浏览器网络记录中无 Dify/第三方密钥；
- 日志和本地元数据无令牌与正文泄露。

### 18.5 Alpha 退出标准

内部 Alpha 结束必须同时满足：

- 1-1、2-6、1-2 各完成至少 3 组真实 Dify 运行；
- 三项首发能力的模型/Token/重试预算和 P50/P95 内部成本验证通过；
- 用户报价与账单均只出现 ¥1/¥3/¥5 `service_fee`；
- 本地可行动 P0-P2 缺陷为 0；
- 重复扣费为 0；
- 报价与结算不一致为 0；
- 失败释放/退款测试全部成功；
- 上传前确认覆盖率为 100%；
- 产物写回成功且不覆盖已有文件；
- Dify 和第三方密钥零客户端透传；
- 至少由一名技术开发人员和一名专利代理人完成端到端试用；
- 所有已知专业限制已在能力卡和结果中披露。

## 19. 发布与回滚

### 19.1 发布顺序

1. 商业平台 `/v1` API 和旧接口适配；
2. 三项能力 Manifest 与白名单；
3. Dify 候选版本验证和发布；
4. DSH Host Plugin；
5. DSH Client Extension；
6. Profile 和 Skill Bundle；
7. 内部账户灰度；
8. 扩大到受邀用户。

### 19.2 回滚策略

- 能力问题：服务端将版本设为 `suspended`，不要求立即卸载插件；
- 价格问题：停止创建报价，保留历史报价和账单；
- Dify 问题：停止映射到问题版本，不覆盖旧版本；
- 插件问题：回滚 Profile 推荐版本，保留本地任务和产物；
- 账务问题：暂停结算并以流水补偿，不删除历史记录；
- 安全问题：撤销令牌、暂停插件版本、通知受影响用户并启动事件响应。

### 19.3 禁止做法

- 不直接覆盖已发布的 Dify 版本或能力合同；
- 不删除历史账单、报价和任务以“修复”对账；
- 不让旧插件继续按本地缓存价格创建任务；
- 不用新的同名文件覆盖用户已有产物；
- 不在未取得浏览器和运行证据时宣称正式可用。

## 21. 依赖、假设与风险

### 21.1 关键依赖

- DSH 可用的插件、客户端扩展、Profile 和凭据机制；
- 商业平台可增加 `/v1` 门面、设备授权和余额冻结；
- 商业平台可记录每任务内部模型、Token、工具和人民币成本，并实施版本预算门禁；
- Dify 工作流有可固定的发布版本；
- 文件服务支持用途绑定和有限期访问；
- 专业能力负责人可提供代表性用例和验收结论。

### 21.2 已决策假设

- DSH 免费；
- 用户调用标准 Dify 专业能力时只支付按次服务费，不支付 Token、模型或运行附加费；
- Basic/Fast/Pro 分别为 ¥1/¥3/¥5；
- 每个节点单独报价和确认；
- 旧网站工作台逐步淘汰，但保留轻量 Web 控制台；
- 服务端主 Markdown 是后续节点的权威交接文件。

### 21.3 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| DSH API 快速变化 | 插件失效 | 版本锁定、兼容矩阵、单一适配层、受控升级 |
| ¥1/¥3/¥5 覆盖不了模型和标准运行成本 | 单位经济失衡 | 模型分层、Token/重试预算、缓存、早停、调整既有档位或暂停版本；不向用户追加费用 |
| 内部成本不可观测 | 低价任务长期亏损 | 按 `job_id + capability_version` 记录模型、Token、工具和人民币成本，监控 P50/P95 |
| 实际 YAML 与 V3.2.0 合同不一致 | 结果无法进入节点链 | 上线前逐能力运行和输出合同验收 |
| 专利数据源授权不清 | 合规和商业风险 | 1-3/3-8 上线前完成许可核验 |
| AI 输出被误用为法律意见 | 专业责任风险 | 限制说明、状态、人工门、适格人员复核 |
| 重复请求重复扣费 | 信任和财务风险 | 服务端唯一幂等约束、冻结/结算分离、三向对账 |
| 项目材料泄露 | 重大信任风险 | 本地优先、最小上传、明确确认、短期令牌和日志脱敏 |
| 迁移中断 | 用户流失 | 并行期、导出、只读归档和明确退役门槛 |

## 23. 产品结论

P0 的最小正确产品不是一个新的三栏专利网站，而是：

1. 一个版本受控的 DSH Profile；
2. 一个连接商业平台的薄插件；
3. 一组免费、可发现专业任务的 Skills；
4. 一个稳定、版本化且可计费的 `/v1` API；
5. 三个经过真实 Dify 运行验证的首发能力；
6. 一套以主 Markdown、人工门、幂等账务和本地写回为核心的交付合同。

只有上述闭环取得实际运行、账务、浏览器和专业审阅证据后，才能从内部 Alpha 扩展到受控 Beta。
