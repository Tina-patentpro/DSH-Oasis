# 历史记录多附件导入修正

## 目标和边界

沿用已批准的网站导入故障修复范围；仅修改绿洲插件的历史附件适配及必要响应容量。仍使用原开发副本及固定依赖构建目录，不修改网站、日常 DSH、凭据、已有导入文件或清单，不自动下载、上传、生成、提交或推送。

## 当前证据

- 用户提供网站已下载的权利要求书和生成报告两个 DOCX。只核对文件大小、SHA-256、ZIP CRC 和必要成员，不读取正文。
- 网站现有 `src/utils/file-url.ts` 将字符串按“逗号后紧跟下一个 HTTP(S) 地址或根路径”拆分，同时支持字符串数组；网站当前页面显示同一历史结果有 2 个生成文件。
- 插件仅接受单个 `file_url` 字符串，把整体传给 `new URL`，列表只提取最后文件名。多个完整地址组成的字符串仍可被 URL 解析器接受，但请求路径错误。
- 这是已确认的代码兼容缺口；本轮未取得生产原始 `file_url` 或失败 HTTP 状态，不能把推定写成已实证的生产根因。旧中文 URL 规范化修复保留。

## 实施合同

1. 用与网站相同的分隔规则解析字符串/字符串数组；普通文件名或查询中的逗号不拆。空项忽略，按规范化后地址去重；非字符串数组项拒绝。
2. 每个附件独立列表、独立选择，key 使用历史 ID 和规范化地址摘要，不把地址送到 Client。下载前再次核对项目/历史归属和所选地址仍在当前附件集合中；重排不换文件，移除/替换拒绝。不下载未勾选的兄弟附件。
3. 逐个保持固定 HTTPS origin、现有路径白名单、无用户信息/片段、文件名安全和 4096 字符 URL 限制。不扩展来源、相对路径、重定向或 Bearer 发送权限。
4. 沿用每页 20 条历史记录的分页含义。多附件会超过旧 40 展示项假设，将列表响应上限对齐既有 2000 项选择票据容量；超量明确拒绝，不静默截断。每次最多导入 100 项、32 MiB 单文件及 100 MiB 总量保持。
5. 原名保存、无覆盖编号、同内容跳过规则不改；旧单附件清单不重写。重新读取后才使用新选择 key。

## 验证与停止条件

- 先写失败回归：合并地址的两文件分别下载、数组/编码/重排/去重、普通逗号、移除与不可信地址、仅选一项及超过 40 项的真实服务响应/落盘。
- 使用原固定依赖目录和既有离线网络保护，定向红绿后完整 build/test/pack dry-run；保留增量与源码/构建哈希。
- 若触及真实凭据、需放宽来源、出现无关工作区漂移或需修改网站，停止相关动作。
- 安装前需要用户确认原开发副本已保存退出；不能覆盖仍运行的插件。安装后再由用户仅选择这两份尚未成功的附件，核对落盘及原生打开；不重复已成功内容。
- 离线验证只覆盖代码，不代替本批安装包和真实下载验收。
