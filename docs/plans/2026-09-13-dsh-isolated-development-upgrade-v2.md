## 执行顺序与验收

1. **S0 保全与快照**：核对当前 Git、实际进程、活动 Profile、程序/配置指纹；保存当前源文件快照及来源 HEAD。正常日志、缓存、窗口状态自写单列，不把其变化直接归因副本。日常关键身份不明即停止。
2. **S1 独立候选**：新目录内固定 exe、私有 Node、Home、Profile、userData、临时/缓存/日志和合成 Workspace；不继承用户 PATH、模型密钥、NODE_OPTIONS；普通文件复制，不共享链接或原配置。拒绝重复启动，保留宿主原生单实例锁；先测试启动边界再启动。程序、实际依赖、锁文件和自有启动器分别记录 SHA。
3. **S2 最小并行验收**：日常先开、候选后开；核对各自主进程/端口/数据 owner、重复启动单写者；用户在候选编辑唯一合成 Markdown，磁盘重读；候选正常退出/重启，日常继续可用且保护指纹无异常。反向顺序由用户自行处理空闲日常实例，不由助手结束。未完成不得进入 S3。
4. **S3 正式适配**：在隔离源快照内迁移原生 keyed Sidebar、公开 Connection 及 attachmentIds 边界；不复制探针业务路由，不读私有 store/DOM、不替换原生单槽。定向恢复必要 Markdown/文件安全能力；缺能力则禁用相应动作，不能冒充兼容。
5. **S4 业务连续性**：保留当前阶段 5 离线 API 接线成果；验证相同输入/来源切换、审核/保存/引用及项目隔离。真实服务绑定、TXT 合同与调用证据保持单列，历史授权不重置。
6. **S5 候选交付**：锁定实际解析依赖、上游 revision、补丁 revision/capability；做一次包级 verify、最终候选隔离复验、与旧开发数据克隆匹配的升级/回滚。禁止两个 Host 同写存储。
7. **S6 后续门禁**：实际模型/API/上传/费用、日常迁移、发布分别取得必要明确授权与对应证据；不由本计划推定完成。
